## Research findings and reuse decision

### A. Journal snapshot and concurrency

- **VERIFIED — Python 3.15.2 thread-safety documentation:** the documented guarantees on this page apply to free-threaded Python builds (GIL disabled). It distinguishes compatible operations (caller must synchronize), shared-object-safe operations (internal synchronization), and atomic operations. It specifically notes that traversals can be affected by concurrent modifications even where individual reads are atomic. Source: https://docs.python.org/3/builtins/threadsafety.html
- **VERIFIED — PostgreSQL 18 transaction-isolation documentation:** Repeatable Read gives a stable transaction snapshot beginning at the first relevant statement; it will not see later concurrent commits. Serializable additionally prevents serialization anomalies but may abort a transaction, requiring retry. PostgreSQL 18.7 release information is dated 2026-11-12 and the docs list 18 as supported. Source: https://www.postgresql.org/docs/current/transaction-iso.html
- **INFERRED — PocketCode consequence:** a coherent snapshot and a fresh snapshot are different properties. Deriving evidence inside `create_receipt` closes caller-controlled age between capture and receipt request. A shared critical section (or database transaction/lock) is still needed if append can run concurrently while the journal reads observation high-water, accepted high-water, and conflict references. The implementation must define a linearization point.
- **Decision:** do not claim thread safety for the current in-memory EventJournal. For the next model implementation either (a) explicitly document single-threaded/non-thread-safe use and ensure capture derives all evidence in one synchronous method, or (b) implement one journal lock used by every append and the entire evidence-capture read. Do not add optimistic claims based on the GIL or list.append behavior.
- **Boundary:** a live EventJournal reference proves only which in-process journal supplied a cut. It does not authenticate the producer, validate an external caller, persist history, or prevent a caller from creating a different journal with fabricated model inputs.

### B. Transactional outbox and replay

- **VERIFIED — Debezium 3.7 documentation is labelled latest stable; 3.8 is development.** The Outbox Event Router expects inserts into an outbox table, captures outbox-table changes, maps an event ID into a message header, and uses the aggregate/event key to preserve partition ordering. Source: https://debezium.io/documentation/reference/transformations/outbox-event-router.html
- **VERIFIED — Apache Kafka design documentation:** delivery semantics separate producer publication durability from consumer processing. At-least-once delivery permits redelivery; exactly-once across an external destination requires cooperation with that destination, typically atomically coordinating destination output with consumed position or using deduplication. Source: https://kafka.apache.org/design/
- **VERIFIED — Temporal Activity documentation:** an activity can complete its side effect and lose its completion acknowledgement if the worker crashes; retry can execute it again. Idempotency keys must be enforced by the external service/consumer, not merely generated by the workflow. Source: https://docs.temporal.io/activity-definition
- **INFERRED — PocketCode consequence:** the grant model's single in-memory commit point remains a useful state-transition model, not an atomic durable outbox. Keep one stable logical outbox event identity across retries; do not mint a new event or aggregate transition when acknowledgement is lost. A consumer must atomically record its accepted identity and resulting state, or remain explicitly at-least-once with an idempotent state transition.
- **Decision:** retain current model-only status; do not introduce Debezium, Kafka, Temporal, a database, a relay, or any hosted dependency. Reuse principles only: stable event identity, append-only outbox rows, aggregate-scoped ordering key, at-least-once dispatch, consumer deduplication, and state+inbox atomicity as a future adapter requirement.

The returned page view did not expose enough license text to classify all three confidently. Exact SPDX/license compatibility therefore remains **UNKNOWN** for this pass. No code, snippets, dependencies, or infrastructure were copied/adopted. Recheck the exact pinned repository commit and license before any code reuse.

## Concrete receipt API contract

Replace detached-snapshot provenance with an API of this shape (design contract, not applied code):

```python
def create_receipt(
    self,
    *,
    effect_id: str,
    attempt_id: str,
    journal: EventJournal,
    # existing non-provenance receipt fields remain unchanged
) -> ResultReceipt:
    evidence = journal.capture_receipt_evidence(
        effect_id=effect_id,
        attempt_id=attempt_id,
    )
    # validate exact scope and evidence invariants;
    # fingerprint from this internally captured evidence;
    # never accept caller watermarks/conflict refs as provenance.
```

Required semantics:

1. `capture_receipt_evidence` is called inside `create_receipt`; no public detached snapshot parameter is accepted.
2. It returns one internally derived cut: journal-global observation high-water, journal-global accepted-event high-water, and conflict sequence references filtered to the exact `(effect_id, attempt_id)`.
3. The capture operation has one defined linearization point. If concurrent append is supported, append and the whole capture share the same journal lock. Otherwise document the journal as not thread-safe and prohibit concurrent access.
4. Invariants: `0 <= accepted_high_water <= observation_high_water`; conflict references are positive, ordered, unique, and no greater than observation high-water; booleans are not accepted as integers; scope matches exactly.
5. A conflict appended after the capture point belongs to a successor receipt/revision. It must not mutate the predecessor fingerprint or its conflict-reference tuple.
6. This is model provenance, not cryptographic authenticity. Producer signatures/credentials, durable storage, cross-process ordering, and tamper resistance remain adapter/security obligations.

## Required regression packet

### Receipt and journal
- Live journal: accepted event seq 1, scoped conflict seq 2; receipt records observation high-water 2, accepted high-water 1, conflict refs `(2,)`.
- Stale detached snapshot: capture before seq 3 conflict, then call receipt creation; old snapshot path is absent/rejected, and internally captured evidence includes seq 3 if it precedes the capture point.
- Exact scope: conflict for effect A/attempt A and effect B/attempt B; receipt A references only A's conflicts while high-waters remain journal-global.
- Invalid high-waters: reject accepted high-water above observation high-water; reject booleans where integer sequence values are expected.
- Invalid conflict refs: reject zero, negative, duplicate, unordered, or above-cut references.
- Successor: late conflict produces revision N+1; N's fingerprint/references remain byte-for-byte unchanged.
- Concurrency contract: if lock mode is chosen, coordinate append and capture with barriers and assert every snapshot is a coherent journal prefix. If single-threaded mode is chosen, test/document the API contract and do not claim a concurrency guarantee.

### Grant/outbox replay
- Same transition and canonical payload is a semantic no-op: no aggregate-version increment, event, or outbox row.
- Changed transition advances once and appends one matching event/outbox row at the same model commit point.
- Same source+event ID and same canonical bytes redelivered: one logical application; return original disposition.
- Same source+event ID with changed canonical bytes: conflict/quarantine; accepted state and watermark do not advance.
- Lost publication acknowledgement: retry the exact stable outbox identity; do not mint a new transition or event.
- Future/out-of-order aggregate version: no silent skip; enforce the documented buffer/reject rule and preserve state.
- Consumer crash after output but before ack: inbox/dedup identity and state update must be atomic in any durable adapter; otherwise do not claim exactly-once effect.

## Red-team corrections to prior claims

1. **Snapshot freshness vs snapshot consistency:** the old recommendation to derive inside receipt creation fixed the detached-snapshot TOCTOU but did not say how multi-field capture is coherent under concurrent append. Correction: specify the linearization point and lock/non-thread-safe alternative above.
2. **Python thread-safety scope:** citing Python thread-safety guidance without its scope risks generalizing free-threaded-build guarantees to all Python builds. Correction: the current page explicitly scopes its detailed guarantees to free-threaded builds; use a journal lock as the model's explicit contract, not assumptions about interpreter internals.
3. **Outbox atomicity vs transport delivery:** describing aggregate+outbox as one commit point can be misread as durable atomicity or exactly-once dispatch. Correction: it is an in-memory model commit point only; external dispatch is at-least-once unless receiver-side dedupe is durable and coordinated with its state.
4. **Exactly-once wording:** Kafka/Temporal patterns do not make arbitrary external side effects exactly once. Correction: exactly-once effect requires destination cooperation and atomic state/identity recording, not just producer retries or stable keys.
5. **CI event SHA vs arbitrary ref:** a workflow's event SHA is trustworthy only if the job checks out and asserts that exact SHA. Correction: print and assert the resolved checkout SHA, and report historical and current lanes separately.
